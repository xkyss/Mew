# 插件生命周期：两对词分层（安装/卸载 × 启用/禁用），加载/卸载退出用户词汇

> **一句话定调：存在性归「安装/卸载」，参与度归「启用/禁用」，运行态「加载/卸载」退回引擎内部——插件行永远只有一个动作，崩溃行把动作换成重启。**

v0.2.1/v0.2.2 已把三层插件宿主、宿主独立启动与「禁用即不拉起」落进代码（ADR-000201/000202），但生命周期语言仍含混：中文「卸载」一词同时压着 *uninstall*（移除）与 *unload*（运行态释放）两个概念，讨论与文档反复在「要不要两对功能」上绕圈；设置→插件行也只按 `enabled` 推「已启用/已禁用」标签，T2 禁用后本次会话仍加载着却已显示「已禁用」，是句谎言；且 `plugins.json` 现状宿主与扩展主机两端都写（`PluginHostApp` 直接 `SetEnabled+Save`），与 000202「单一事实来源」矛盾，并发写有竞争。本 ADR 把生命周期词汇、状态语义与权力边界一次钉死。

## Considered Options

- **每插件暴露两对独立开关（启用/禁用 + 加载/卸载）**：四个正交状态（已启用未加载、已禁用仍加载…）对用户几乎全无价值，个人启动器里「禁用却仍驻留服务」没有意义；且 T2 的 ALC 卸载是 best-effort，真做「卸载」按钮等于承诺一件可能静默不发生的事。→ 未选。
- **Windows 服务式语义（禁用 = 只拦下次启动，运行中的需另设停止）**：为制造第二对用户开关而引入「禁用但仍在跑」状态，得不偿失。→ 未选。
- **纯 VS Code 式（禁用一律下次重载生效）**：对 T3 是浪费——独立进程本就该能当场杀掉，v0.2.2 故事 20 已承诺「禁用独立插件后来源立即从浮层消失」。→ 未选。
- **VS Code 词法 + 按隔离能力分型（选定）**：见下。

## 决策

**1. 词汇：两对用户词，各管一轴。**

- **安装/卸载（install/uninstall）= 存在性**：插件目录出现在扫描范围内即「已安装」；「卸载」一词**专指 uninstall**（把插件目录移出受管范围）。v0.2.x 不设卸载按钮——目录增减（设置→插件→插件目录管理 + `MEW_PLUGINS_EXTRA`）已覆盖该职责，「卸载」先作为词汇与存在性状态位存在。
- **启用/禁用（enable/disable）= 参与策略**：持久化于 `plugins.json`（`{[id]: enabled}`），缺省启用。
- **「加载/卸载（load/unload）」退出用户词汇**，退回引擎内部动词（T2 ALC 装载、T3 进程拉起/杀）；中文文档与 UI 不再用「卸载」指运行态释放，需要时用「回收/释放/拉起/杀掉」，代码保留英文 `Load`/`Unload`。

**2. 禁用语义 = 停 + 回收**（非 Windows 服务式「只拦下次启动」）。每插件行 = 一个状态标签 + 一个动作，无第二开关。

**3. 生效时机按隔离能力分型。**

- **T3（独立进程 exe）：禁用立即回收**——宿主杀进程，其搜索源/设置节/热键当场消失（兑现 v0.2.2 故事 20）。
- **T2（dll，同扩展主机进程）：禁用意图先落 `plugins.json`，下次主界面启动不再装载**——不做运行时 ALC 卸载，绕开 best-effort 卸载死结；行上副提示「重启扩展主机后生效」，本会话不谎称已停。

**4. 崩溃按进程归因。**

- **每插件行「已崩溃」只属于 T3**：宿主探活发现独立进程退出/断连即标记；行内动作变「重启」（宿主重新拉起进程），不用「先禁用再启用」绕圈。
- **T2/T1 崩溃 = 扩展主机进程崩溃**（同进程无隔离）：没有「单个 T2 已崩溃」状态；恢复动作是宿主级「重启扩展主机」（000202 已确立）。

**5. 崩溃态不落盘。** 崩溃是运行态推导，不进 `plugins.json`；宿主重启后仍按启用态正常拉起（崩溃多半是一次性的：休眠唤醒、手动杀、外部环境）。防循环只做运行期计数：启动后短时间崩 N 次 → 本次运行不再自动拉起，标「已崩溃」待手动「重启」。

**6. 行标签契约 = 策略单标签 + 健康态覆盖。** 主词永远反映持久策略（已启用/已禁用）；清单错误 / ID 重复 / 需 JIT / 已崩溃为健康态**覆盖**策略词；健康行动作 = 单按钮（已启用→「禁用」，已禁用→「启用」），已崩溃行动作 = 「重启」。

**7. `plugins.json` 写权力归一宿主。** 兑现 000202「发现 + 启用态只留宿主一份」：扩展主机面板的开关操作不再自行 `Save()`，改为经 IPC 请求宿主落盘（消除双进程并发写竞争）；扩展主机面板收窄为只列 T1/T2（过滤 exe 行），T3 行的状态/开关/重启 UI 归宿主侧（宿主窗口/托盘入口，不依赖扩展主机活着）。

**8. 空闲卸载记将来范围外。** 「重 T3 保持已启用但平时不驻留、需要时才拉起」将来是**宿主级单一策略开关**，不是每插件第二个开关；现有两轴模型（存在性 × 策略）足以让它在将来无痛切入。

## Consequences

- `PluginHostApp.RefreshPluginPanel` 行逻辑要改：按健康态 + 启用态呈现单标签（含「已崩溃」不再只存在于 `PluginHealth` 枚举里），T2 切换后补「重启扩展主机后生效」副提示；`PluginHealth.Disabled/Crashed` 从此真正被使用。
- `PluginHostApp` 的开关写路径改为经宿主（IPC）落盘；宿主获得 T3 管理 UI 与崩溃防循环计数，T3 行「重启」动作接线到独立进程拉起。
- `plugins.json` 读写模型收敛为宿主唯一写者；快照协议不变。
- 词汇表（CONTEXT.md）新增「插件启用/禁用」「插件安装/卸载」两词，并写明「卸载」仅指 uninstall；`docs/run.md` 与后续文档的「卸载 ALC」式措辞全部改为「回收/释放」。
- 本 ADR 是 000201/000202 的**语义补丁**，不推翻三层结构、宿主独立启动与「exe 生死宿主全权」：它只把 000201「禁用→卸载 ALC」的措辞在 T2 上改写为「下次启动不再装载」，把 000202 已宣告但未落地的「宿主唯一写 / 宿主侧管理 exe」补上边界。
- 术语不变（CONTEXT.md 插件=T2+T3、独立插件=T3、扩展主机=Layer2 继续有效）。

## Alternatives Rejected

- 见 Considered Options；「两对独立开关」「Windows 服务式禁用」「纯 VS Code 式统一重载」均因对个人自用启动器无价值或浪费隔离能力而放弃。
